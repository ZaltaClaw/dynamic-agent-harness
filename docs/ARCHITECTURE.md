# Architecture

## Design goal

Separate the organization-owned harness contract from any model vendor or deployment engine. The starter has four ports:

1. **Spec:** identity, model reference, tools, skills, runtime limits, context policy, approvals, sandbox policy, and storage target.
2. **Runtime adapter:** turns a task into ordered progress/tool/subagent/approval/artifact events.
3. **Store:** persists run metadata, append-only events, and artifacts.
4. **Transport:** REST for commands and SSE for resumable observation.

The bundled deterministic runbook is an executable conformance adapter. It proves the harness, not model intelligence.

## Composition principles

The repository applies three ideas from DeepSeek Harness without importing its developer-preview runtime:

- Every operational component sits behind a replaceable port: model/workflow, store, job runner, sandbox, and policy.
- Templates behave as profile layers over one portable base spec; organizations own the final composed manifest.
- Model-visible progress must be reconstructable from persisted run records and ordered events. Transient UI state is never the source of truth.

A production extension should define the capability interface, provide an implementation, and connect at least one consumer. Shipping only a provider-specific UI control is not a complete capability seam.

## Run state machine

```text
created
  -> running
     -> capability discovery
     -> zero or more independent worker branches (bounded by maxParallel)
     -> no declared blueprint writer -> completed
     -> declared blueprint.write -> waiting_for_approval
        -> allow -> blueprint compilation + artifact write -> completed
        -> deny  -> tool denied                         -> completed
  -> failed
```

The approval ID is generated by the runtime and stored on the run. Resolution does not depend on an in-memory promise, so a replacement runtime instance can resolve the persisted checkpoint. The artifact's public logical path is unavailable before the matching approval resolves to `allow`; absolute host paths are never part of the public record or event payload.

Bundled worker branches receive separate in-memory context objects and isolation IDs so their summaries do not share mutable branch state. They are not process, container, or security boundaries; `runtimeContract.parallelIsolation` and `sandboxedExecution` remain `false` until a production adapter supplies those guarantees.

## Event model

Each event contains:

- stable ID
- run ID
- monotonically increasing per-run sequence
- event type
- timestamp
- structured payload

Event payloads carry observable progress summaries. They must not expose hidden chain-of-thought, secrets, raw authorization headers, or unnecessary tool payloads.

The JSONL adapter serializes each append behind in-process and filesystem locks. A fresh store instance can reconstruct the run and list events after a sequence cursor. The run JSON record is authoritative for current and terminal state; events are the ordered observation log. This adapter is intentionally single-host and is not a cross-file transactional database.

## Browser disconnects

Execution is started server-side and is not tied to the SSE request. The SSE route first replays persisted events and then subscribes to new appends. On reconnect, the client supplies its last sequence and receives only later events.

This survives a browser disconnect while the server continues. A persisted approval checkpoint can be resolved after a runtime object is replaced, but active pre- or post-approval execution is not automatically leased and resumed after a host crash. Production deployments must add a queue/lease adapter for that guarantee.

## Context controls

The portable spec captures four long-running controls:

- deferred capability loading
- large-result offloading
- compaction after an input-token threshold
- isolated subagents that return compact conclusions

The deterministic adapter records these in the generated blueprint. A model adapter is responsible for applying them to actual model context.

## Safety boundary

Schema validation rejects an enabled write/delete tool without its matching approval risk. The local runtime executes only declared, enabled capabilities; it pauses before its supported `blueprint.write` mutation and verifies the exact persisted approval ID. System prompts may explain policy, but they are never the enforcement layer.
